Every field Leap accepts has one canonical name, written `scope.field`. Send those names on [Look up incentives](/api-reference/incentives-lookups/look-up-incentives) and [Refresh incentives](/api-reference/incentives-lookups/refresh-incentives), which is the path we recommend. The same names carry over to an application through one mechanical rule, so you map your data to Leap once. Use this page to build request bodies, and to plan what you claim under **Data Preferences**.

## One key name, two renderings

There are two scopes: `customer` for facts about the applicant, and `customer_device` for facts about one installation. The scope is part of the name, so `customer.email` and `customer_device.purchase_date` are the names themselves rather than a path to them.

**On a lookup or a refresh**, send the canonical name exactly as written, as a key. Customer-scope keys go in `customer_details`. Installation-scope keys go in the `details` object on the matching `customer_devices[]` entry. Values are always strings.

```json
{
  "reference_id": "customer-123",
  "customer_details": {
    "customer.utility_account_number": "0123456789"
  },
  "customer_devices": [
    {
      "device_id": "d290f1ee-6c54-4b01-90e6-d701748f0851",
      "details": {
        "customer_device.purchase_price": "699.00"
      }
    }
  ]
}
```

**On an application**, drop the scope prefix and nest the field under the object that scope names. `customer.` fields go inside `customer`. `customer_device.` fields go inside the matching entry of `customer_devices[]`. Values carry their real JSON type.

```json
{
  "customer": {
    "utility_account_number": "0123456789"
  },
  "customer_devices": [
    {
      "id": 78,
      "purchase_price": 699.00
    }
  ]
}
```

The scope is the same on both sides. A lookup writes it into the key, and an application writes it into the shape:

| Canonical name | On a lookup | On an application |
| --- | --- | --- |
| `customer.utility_account_number` | key in `customer_details` | property of `customer` |
| `customer_device.purchase_price` | key in that device's `details` | property of that `customer_devices[]` entry |

<Warning>
  The lookup key set is closed, even though the schema accepts any string key. An unrecognised key returns 400 for the whole request. One typo therefore costs you the eligibility answer for every program, not only that field. Leap checks `customer_details` and every device's `details` together before writing, so one call reports every bad key.

  An application behaves the other way. It drops a property it does not recognise and still returns success, so a misspelled name is lost silently.
</Warning>

### Value forms a lookup accepts

Every lookup value travels as a string, and Leap parses it into the type the field expects:

- **Booleans**: send `true` or `false`.
- **Dates**: send `YYYY-MM-DD`.
- **Numbers**: send digits with an optional decimal point, no currency symbol and no thousands separator.
- **Enums**: matched without regard to case, so send the documented value as written.

An absent key, a JSON `null`, and a blank string all mean the value is not supplied. None of the three stores anything.

## The fields

Send these on [Look up incentives](/api-reference/incentives-lookups/look-up-incentives) when you have them at quote time, and on [Refresh incentives](/api-reference/incentives-lookups/refresh-incentives) as you learn the rest. These 31 names are the whole lookup set: any other key returns 400.

The **On an application** column gives the same field's property name there, so you can carry one mapping through both APIs.

| `customer_device.warranty_months` | number | `customer_device.warranty_months` |
| `customer_device.pto_date` | date | lookup and refresh only |
| `customer_device.installer_license` | string | use `customer_device.contractor_license` |
| `customer_device.vehicle_registration` | presence | supply the `VEHICLE_REGISTRATION` attachment |

Three rows do not carry straight across:

- **`pto_date`** has no writable property on an application yet, so send it on a lookup or a refresh.
- **`installer_license`** is the same fact as `contractor_license`, which both APIs accept. Send `contractor_license` and ignore this one.
- **`vehicle_registration`** is a possession check rather than a value. Leap reads whether you supplied something, not what you supplied, so it does not hold a vehicle identifier. Send the document itself as a `VEHICLE_REGISTRATION` attachment, and send the VIN as `customer_device.vehicle_vin` on an application.

**Eligibility only** marks a fact Leap evaluates but does not keep on an application. Send it on a lookup or a refresh and nowhere else. Vehicle count comes from the devices you register rather than from a field, and the four PG&E rows are enrollments the program checks rather than data an application holds.

## What claiming a field changes

Claiming a field moves responsibility for it from the customer to you. When you claim one under [**Settings → Data Preferences**](https://partner.incentives.leap.energy/settings/data-preferences), that field is:

- Removed from the customer-facing application form
- Your responsibility to keep accurate and up-to-date

Claimed fields reappear for any device the customer adds themselves, so Connect still collects them in that case.

<Tip>
Start by claiming fields you already collect across all customers. You can expand to handle territory-specific data over time.
</Tip>

<Note>
You don't need to claim all fields in a category. Focus on what you can reliably provide with high accuracy. Start with HIGH frequency fields for maximum impact.
</Note>

Frequency below rates demand for a field across the utilities Leap covers, as HIGH, MEDIUM, or LOW. Fields added since that survey carry no rating.

## What the customer always supplies

Signatures and attestations stay with the customer, and no API accepts them on their behalf. That covers a program's terms acceptance, its eligibility attestations, and the per-program agreements a program administrator requires the applicant to sign. Leap collects every one of them in Connect, and claiming a field never moves them to you.

The four `customer.pge_*` enrollment keys are the exception. Each records an enrollment the customer completed with PG&E rather than a signature Leap needs to collect, so a lookup accepts them like any other customer attribute.

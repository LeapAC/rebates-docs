Two Leap APIs take customer and installation data, and they spell the same facts differently. This page gives every field three things: its Applications API property name, the prefixed key a lookup takes, and its type. Use it to plan what you claim under **Data Preferences**, and to build bodies that pass validation first time.

## How the two APIs name the same field

The notation differs by API, and sending one API's spelling to the other does not work.

An incentives lookup takes flat, prefixed keys whose values are always strings. Customer facts go in `customer_details`, and installation facts go in the `details` object on the matching `customer_devices[]` entry:

```json
{
  "reference_id": "customer-123",
  "customer_details": {
    "customer.utility_account_number": "0123456789"
  },
  "customer_devices": [
    {
      "device_id": "d290f1ee-6c54-4b01-90e6-d701748f0851",
      "details": {
        "customer_device.purchase_price": "699.00"
      }
    }
  ]
}
```

The Applications API takes bare property names nested under `customer` or `customer_devices[]`, with real JSON types:

```json
{
  "customer": {
    "is_homeowner": true
  },
  "customer_devices": [
    {
      "id": 78,
      "purchase_price": 699.00
    }
  ]
}
```

One fact, two spellings: the equipment price is `customer_device.purchase_price` as a string on a lookup, and `purchase_price` as a number on an application.

<Warning>
  The lookup key set is closed, even though the schema accepts any string key. An unrecognised key returns 400 for the whole request. One typo therefore costs you the eligibility answer for every program, not only that field. Leap checks `customer_details` and every device's `details` together before writing, so one call reports every bad key.

  The Applications API behaves the other way. It drops a property it does not recognise and still returns success, so a misspelled name is lost silently.
</Warning>

### Value forms a lookup accepts

Every lookup value travels as a string, and Leap parses it into the type the field expects:

- **Booleans**: send `true` or `false`.
- **Dates**: send `YYYY-MM-DD`.
- **Numbers**: send digits with an optional decimal point, no currency symbol and no thousands separator.
- **Enums**: matched without regard to case, so send the documented value as written.

An absent key, a JSON `null`, and a blank string all mean the value is not supplied. None of the three stores anything.

Every other field on this page belongs to the Applications API alone. Send those with [Update application](/api-reference/applications/overview), which accepts a wider vocabulary than a lookup does. Its published schema lists the common properties rather than every one it accepts. Ask Leap if you need a field you cannot find.

## What claiming a field changes

Claiming a field moves responsibility for it from the customer to you. When you claim one under [**Settings → Data Preferences**](https://partner.incentives.leap.energy/settings/data-preferences), that field is:

- Removed from the customer-facing application form
- Your responsibility to keep accurate and up-to-date

Claimed fields reappear for any device the customer adds themselves, so Connect still collects them in that case.

<Tip>
Start by claiming fields you already collect across all customers. You can expand to handle territory-specific data over time.
</Tip>

<Note>
You don't need to claim all fields in a category. Focus on what you can reliably provide with high accuracy. Start with HIGH frequency fields for maximum impact.
</Note>

Frequency below rates demand for a field across the utilities Leap covers, as HIGH, MEDIUM, or LOW. Fields added since that survey carry no rating.

## Installation fields

These fields describe one installation: what was bought, when it went in, and who put it there. Installation contractors and retailers are usually best placed to supply them. Each field belongs to a single `customer_devices[]` entry, so a customer with two installations carries two sets.

<AccordionGroup>
  <Accordion title="Cost (4 fields)" icon="dollar-sign">
    Only `purchase_price` and `installation_cost` reach the incentive calculation. See [How cost-based programs are priced](/api-reference/incentives-lookups/overview#how-cost-based-programs-are-priced).

    <ResponseField name="purchase_price" type="number">
      **Frequency:** MEDIUM · **Lookup key:** `customer_device.purchase_price`

      The retail price paid for the equipment only, excluding installation labor and materials. Used to verify rebates don't exceed equipment cost and for calculating percentage-based incentives.
    </ResponseField>

    <ResponseField name="installation_cost" type="number">
      **Frequency:** LOW · **Lookup key:** `customer_device.installation_cost`

      The cost of professional installation including labor, materials, permits, and any electrical/plumbing work. Separate from equipment cost to allow programs that reimburse installation separately.
    </ResponseField>

    <ResponseField name="total_project_cost" type="number">
      **Lookup:** not accepted

      Total project cost as your own records hold it. The incentive calculation does not read it, so a cost-based program prices from `purchase_price` and `installation_cost` alone.
    </ResponseField>

    <ResponseField name="net_cost" type="number">
      **Lookup:** not accepted

      Project cost after other incentives, as your own records hold it. The incentive calculation does not read this one either.
    </ResponseField>
  </Accordion>

  <Accordion title="Dates (3 fields)" icon="calendar">
    <ResponseField name="purchase_date" type="date">
      **Frequency:** HIGH · **Lookup key:** `customer_device.purchase_date`

      Date when the equipment was purchased. Must fall within program year dates and is used to verify eligibility timing requirements.
    </ResponseField>

    <ResponseField name="installation_date" type="date">
      **Frequency:** MEDIUM · **Lookup key:** `customer_device.installation_date`

      Date when the equipment was fully installed and operational. Critical for determining application deadlines (e.g., must apply within 30/60/90 days) and program year eligibility.
    </ResponseField>

    <ResponseField name="customer_device.pto_date" type="date">
      **Lookup key:** `customer_device.pto_date` · **Applications API:** not accepted

      Date the utility granted permission to operate (PTO). Programs that require an interconnected, operating system check it.
    </ResponseField>
  </Accordion>

  <Accordion title="Equipment and permits (8 fields)" icon="wrench">

    </ResponseField>

    <ResponseField name="quantity" type="integer">

    <ResponseField name="permit_number" type="string">

    <ResponseField name="is_new_equipment" type="boolean">
      **Lookup key:** `customer_device.is_new_equipment`

      Whether the equipment is new rather than used or refurbished. Programs that exclude second-hand equipment check it.

      **Lookup key:** `customer_device.inspection_passed`

    <ResponseField name="warranty_months" type="number">
      **Lookup key:** `customer_device.warranty_months`

## What the customer always supplies

Signatures and attestations stay with the customer, and no API accepts them on their behalf. That covers a program's terms acceptance, its eligibility attestations, and the per-program agreements a program administrator requires the applicant to sign. Leap collects every one of them in Connect, and claiming a field never moves them to you.

The four `customer.pge_*` enrollment keys are the exception. Each records an enrollment the customer completed with PG&E rather than a signature Leap needs to collect, so a lookup accepts them like any other customer attribute.
